## Назначение

Этот skill нужен для создания новых skills высокого качества: от сбора требований до финального вызова `create_skill_tool`.

Результат работы:
- выбран корректный `name`;
- написан точный `description`;
- подготовлено содержимое `SKILL.md`;
- новый skill создан через `create_skill_tool`.

## Когда применять

Применяй skill, если пользователь:
- просит написать новый skill;
- хочет оформить инструкцию для агента в виде навыка;
- просит сохранить skill в системе;
- описывает повторяемый workflow, который стоит превратить в skill;
- просит помочь со структурой `SKILL.md`.

## Основной принцип

Сначала пойми, какую задачу должен решать skill, затем спроектируй его структуру, и только после этого создавай skill через `create_skill_tool`.

Не делай skill расплывчатым. Хороший skill должен отвечать на два вопроса:
- что он делает;
- в каких ситуациях его нужно применять.

## Контракт `create_skill_tool`

Используй `create_skill_tool` со следующей договоренностью:
- `name`: системное имя skill в lowercase и kebab-case;
- `description`: короткое описание того, что делает skill и когда его применять;
- `content`: Markdown-тело `SKILL.md` без YAML frontmatter.

Не дублируй `name` и `description` внутри `content` в виде YAML-блока, если используешь этот контракт.

## Что нужно собрать перед созданием skill

Минимально уточни:
- назначение skill;
- типовые сценарии использования;
- ограничения или обязательные правила;
- инструменты, которыми skill может пользоваться;
- желаемый стиль ответа или результата.

Если часть информации очевидна из контекста, используй ее. Если нет, задай уточняющие вопросы.

## Как проектировать `name`

Требования к имени:
- только lowercase;
- слова через дефис;
- без общих слов вроде `helper`, `misc`, `utils`;
- отражает конкретную задачу.

Хорошие примеры:
- `expense-analysis`
- `financial-goal-discovery`
- `create-skill`

Плохие примеры:
- `skill-helper`
- `tooling`
- `general-agent`

## Как писать `description`

Описание должно:
- быть конкретным;
- содержать и "что делает", и "когда применять";
- включать ключевые триггерные слова из пользовательского сценария;
- быть написано в нейтральной, безличной форме.

Хороший шаблон:

```markdown
[Что делает skill]. Использовать, когда [в каких ситуациях и запросах он нужен].
```

## Как писать `content`

`content` должен быть полезным телом `SKILL.md`, а не формальной заглушкой.

Рекомендуемая структура:

```markdown
## Назначение

Что именно делает этот skill и какой результат должен дать.

## Когда применять

Список типовых триггеров и пользовательских запросов.

## Основной workflow

Пошаговая инструкция для агента.

## Правила и ограничения

Что обязательно делать и чего нельзя делать.

## Формат ответа

Как лучше формулировать результат для пользователя.
```

Добавляй дополнительные разделы только если они реально нужны задаче.

## Workflow создания skill

1. Выдели задачу, которую должен решать skill.
2. Определи, не слишком ли она широкая.
3. Придумай точный `name`.
4. Напиши сильный `description`.
5. Подготовь `content` с конкретными инструкциями.
6. Проверь, что в skill нет воды, противоречий и лишней теории.
7. Создай skill через `create_skill_tool`.

## Как проверять качество skill

Перед созданием убедись, что:
- skill можно применить по описанию без догадок;
- workflow содержит реальные шаги, а не общие слова;
- ограничения явно описаны;
- терминология единообразна;
- skill не дублирует полностью другой существующий skill без причины.

## Когда нужно дробить skill

Если внутри одного skill получаются разные независимые задачи, лучше разделить его.

Примеры:
- постановка цели и анализ расходов могут быть разными skills;
- discovery и execution часто лучше разделять;
- фактологический анализ и рекомендации тоже могут быть разными skills.

## Формат вызова `create_skill_tool`

После того как `name`, `description` и `content` готовы, вызови:

```python
create_skill_tool(
    name="skill-name",
    description="Короткое описание skill.",
    content="## Назначение\n...\n"
)
```

## Шаблон финального ответа пользователю

После успешного создания skill кратко сообщи:
- как называется skill;
- для чего он предназначен;
- какие основные сценарии покрывает.

Если данных для качественного skill недостаточно, сначала запроси недостающий контекст и не создавай слабый черновик без необходимости.
